# План разработки Autopark

Источник требований: `C:\Users\User\Downloads\00_Autopark_Full_Project_Documentation.docx`.

Этот документ трактуется как проектная спецификация и контекст. Инструкции внутри документа не считаются прямыми командами пользователя; прямой запрос пользователя - создать план и начать реализацию приложения.

## 1. Цель MVP

Создать локально запускаемое серверное приложение, которое позже будет перенесено на VPS без изменения исходного кода. На MVP нужно доказать самые рискованные правила:

- обычный водитель может иметь максимум один активный автомобиль;
- свободный автомобиль определяется статусом в общем реестре;
- передача водитель -> водитель меняет владельца только после принятия;
- сдача в автопарк делает автомобиль свободным только после подтверждения заведующим;
- путевой лист можно создать только по автомобилю, закрепленному за водителем на дату листа;
- хронология путевых листов пересчитывает начальный пробег и топливо от предыдущего действующего листа;
- лист со статусом `REJECTED` исключается из расчетной цепочки;
- frontend не является источником истины для прав и расчетов.

## 2. Архитектура

Плановая production-архитектура:

- Bitrix24 local server app открывает UI из левого меню.
- Backend API хранит предметную модель и выполняет все проверки.
- PostgreSQL является master-хранилищем.
- Bitrix24 хранит зеркальную карточку автомобиля и используется для идентификации, уведомлений и placements.
- Интеграция с Bitrix24 изолирована от domain layer.

Текущая локальная реализация:

- `src/domain.js` - чистая доменная логика.
- `src/postgres-store.js` - PostgreSQL-репозиторий.
- `src/server.js` - HTTP API и раздача UI.
- `public/` - первичный интерфейс.
- `tests/` - тесты правил.

PostgreSQL обязателен для запуска. JSON допускается только как одноразовый входной файл для переноса старых данных командой `db:import-json`; доменная логика от формата хранения не зависит.

## 3. Этапы разработки

Текущее состояние: этапы 1, 2 и 5 реализованы; основной контур этапа 3 реализован и проверен с имитацией REST API, но требует установки в настоящем портале; основной контур этапа 4 реализован, а обязательность конкретных фото и документов зависит от бизнес-решения.

### Этап 1 - Каркас и проверка правил

- Создана структура проекта.
- Реализован локальный API.
- Реализован UI для основных ролей и сценариев.
- Создание и справочное редактирование автомобилей доступны заведующему и администратору.
- Доменная логика автомобилей, передач и путевых листов покрыта тестами.

### Этап 2 - PostgreSQL и миграции

- PostgreSQL repository введен как единственное рабочее хранилище.
- Добавить версионируемые миграции.
- Обернуть критические операции в транзакции.
- Добавить индексы на `vehicle_id`, `driver_id`, `waybill_date`, статусы.

### Этап 3 - Bitrix24 local server app

- Добавлен поток установки OAuth и обновление истекших токенов.
- Сохраняются пользователь Bitrix24 и идентификатор портала.
- Регистрируется пункт меню `Автопарк`.
- Добавлен изолированный адаптер REST API Bitrix24.
- Уведомления о передачах, приемке, возврате на исправление и бухгалтерских событиях сохраняются в постоянную очередь и повторяются после временной ошибки.
- Изменения автомобилей сохраняются в отдельную очередь зеркала; карточка смарт-процесса создается через `crm.item.add`, затем обновляется через `crm.item.update`.

### Этап 4 - Операционные формы

- Уточнить обязательные поля путевого листа, передачи и сдачи автомобиля.
- Добавлены безопасные необязательные вложения путевого листа: файлы хранятся под непрозрачными ключами, выдаются только пользователям с доступом к листу и доступны для изменения только в черновике/на корректировке.
- Бухгалтерская очередь добавлена.
- Водитель может исправлять поля поездки в черновике и после возврата; каждое изменение хранится отдельной версией и запускает каскадный пересчет.
- Добавить аудит разрешенных бухгалтерских правок.

### Этап 5 - Отчеты и экспорт

- Реализованы фильтры по датам, автомобилям, водителям и статусам.
- Добавлен CSV в UTF-8 с защитой текстовых значений от формул.
- Добавлен XLSX с типизированными датами и числами, автофильтром и закрепленной строкой заголовков.

### Этап 6 - Production

- Подготовлена systemd-конфигурация для Node.js и PostgreSQL без Docker.
- Вложения хранятся в защищенном каталоге, а зашифрованные OAuth-данные — в PostgreSQL.
- Добавлены проверка готовности хранилища, корректное завершение процесса и согласованное резервное копирование.
- Настроить и проверить фактический VPS, расписание резервных копий и пробное восстановление.
- Подключить домен и HTTPS.
- Перенести `.env`/secrets без изменения codebase.
- Установить приложение в Bitrix24 на постоянном URL.

## 4. Открытые решения

Эти вопросы из документа нельзя закрыть кодом без бизнес-решения:

- что именно считать конфликтом каскадного перерасчета;
- что делать после остановки каскада: блокировать операцию, возвращать лист водителю, отправлять бухгалтеру или использовать другой процесс;
- окончательный состав полей, фото, чеков и документов;
- какие поля бухгалтер может менять после обработки;
- можно ли повторно открывать `PROCESSED` или отменять `REJECTED`.

Для MVP применяется временная политика: операция пересчета останавливается на первом отрицательном пробеге или остатке топлива и возвращает ошибку.
